De Bronze a Silver: Avro, parsing y limpieza

Christian Herrera10 min de lectura orientativa
  • ingesta
  • calidad

Objetivo: aprender a transformar los bytes que recibimos de Kafka en una tabla Silver con datos tipados, limpios y preparados para su consumo.

Hoy veremos tres conceptos:

  1. Cómo deserializar Avro.

  2. Cómo limpiar y validar los datos.

  3. Cuándo utilizar spark.read o spark.readStream.

2. ¿Qué significa deserializar Avro?

Imagina que Kafka recibe este ticket:

json
{
  "ticket_id": "T001",
  "pharmacy_id": 109,
  "amount": 125.50
}

Pero en Kafka no tenemos este JSON. Tenemos una secuencia de bytes codificados en Avro.

Para interpretarlos necesitamos conocer su esquema:

json

{
  "type": "record",
  "name": "Ticket",
  "fields": [
    {"name": "ticket_id", "type": "string"},
    {"name": "pharmacy_id", "type": "int"},
    {"name": "amount", "type": "double"}
  ]
}

El esquema describe cómo interpretar esos bytes: el nombre, el orden y los tipos de los campos.

La función que necesitas conocer es from_avro().

Databricks permite utilizarla tanto en transformaciones batch como streaming. Databricks on AWS

3. Nuestro primer Silver con Lakeflow

Para simplificar, utilizaremos un esquema Avro fijo y supondremos que value contiene directamente un registro Avro binario, sin prefijos adicionales.

python

import json
from pyspark import pipelines as dp
from pyspark.sql import functions as F
from pyspark.sql.avro.functions import from_avro

# Contrato Avro de ejemplo
AVRO_SCHEMA = json.dumps({
    "type": "record",
    "name": "Ticket",
    "fields": [
        {"name": "ticket_id", "type": "string"},
        {"name": "pharmacy_id", "type": "int"},
        {"name": "amount", "type": "double"}
    ]
})

@dp.table(name="silver_tickets")
def silver_tickets():

    bronze = spark.readStream.table(
        "bronze_tickets"
    )

    parsed = bronze.withColumn(
        "ticket",
        from_avro(
            F.col("value"),
            AVRO_SCHEMA
        )
    )

    return (
        parsed
        .select(
            F.col("ticket.ticket_id").alias("ticket_id"),
            F.col("ticket.pharmacy_id").alias("pharmacy_id"),
            F.col("ticket.amount").alias("amount"),
            F.col("kafka_timestamp")
        )
        .filter(F.col("amount") > 0)
    )

Observa que seguimos sin utilizar .write ni gestionar checkpoints manualmente.

La transformación lee los nuevos registros de Bronze, interpreta los bytes Avro, selecciona los campos y elimina los tickets cuyo importe no sea positivo.

El código supone que bronze_tickets procede de la lección 5 y que todos los mensajes corresponden al esquema mostrado. Para mensajes de producción con múltiples versiones necesitaremos resolver el esquema correcto.

5. La diferencia entre read y readStream

Esta es probablemente la parte más importante de la lección.

spark.readStream

Incremental
python
spark.readStream.table("bronze_tickets")

Lee los nuevos datos utilizando el progreso registrado en el checkpoint. Es ideal para fuentes append-only y transformaciones de baja latencia.

spark.read

Snapshot
python
spark.read.table("bronze_tickets")

Define una lectura del estado de la tabla. Si se utiliza en una Materialized View, Lakeflow puede optimizar el refresh procesando solo los cambios necesarios.

Ejemplo fundamental:

Supongamos que un ticket ya procesado cambia de 100 € a 150 €.

  • Con readStream, una Streaming Table convencional no propaga automáticamente ese UPDATE y puede fallar al detectar el cambio en Delta.

  • Con read, una Materialized View puede reflejar el nuevo valor al refrescarse.

Por eso no deberíamos elegir siempre Streaming Tables únicamente porque sean más eficientes.

6. ¿Y cómo lo haríamos con Apicurio?

En vuestra arquitectura hay una diferencia importante: no utilizáis un único esquema Avro fijo.

Tenéis contratos, diferentes versiones y headers para identificar los esquemas.

Una posible arquitectura sería:

Bronze raw · value + headers

Identificar el contrato y la versión

x-value-schema-name / version / id

Resolver el esquema Avro

Apicurio / repositorio de contratos

Silver deserializada

Campos tipados y validados

Hay un matiz técnico: si Apicurio devuelve mensajes en formato compatible con Confluent Schema Registry, podemos estudiar la deserialización integrada con from_avro y Schema Registry. Si el mensaje lleva Avro puro y la identificación del esquema va exclusivamente en headers, necesitaremos resolverlo de otra manera. Databricks on AWS

Para producción, procuraría evitar consultas HTTP a Apicurio por cada evento. Es preferible resolver las versiones de los esquemas de forma controlada y reutilizarlas durante el procesamiento.

7. Mini ejercicio

Tenemos una Bronze que recibe tickets de Kafka constantemente, solo con inserciones.

Queremos deserializar Avro y guardar los nuevos tickets en Silver.

¿Qué opción elegirías?

¡Correcto!

Una Streaming Table permite deserializar y transformar incrementalmente los nuevos eventos de una fuente append-only.

Qué debes recordar hoy: from_avro convierte bytes en columnas tipadas; readStream procesa incrementalmente fuentes append-only, mientras que read permite definir una consulta sobre el estado de los datos. La decisión entre Streaming Table y Materialized View depende de cómo cambian los datos, no solamente de su volumen.

En la lección 7 aprenderemos a detectar y controlar datos incorrectos sin depender únicamente de filtros manuales.
